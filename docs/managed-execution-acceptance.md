# Managed execution acceptance cases

## Status and use

**Acceptance requirements, not test results.** These cases accompany the [execution contract](managed-execution-contract.md) and trace to sections of the [conceptual baseline](../pi-decision-tools-design.md). The generic implementation now has deterministic tests with fake classifiers, controlled clocks/signals and real temporary Pi session files. See the [verification map](verification.md) for concrete assertions and remaining audit gaps; a case appearing here does not mean every clause has passed. Provider counts below mean native classifier invocations, not hidden provider HTTP activity.

Unless a row says otherwise: a persisted conversation exists, one compatible owner is enabled, the selected model matches the batch, valid JSON/answers fit bounds, and allowance is sufficient. R/B denote request/input-byte units; B is computed by the contract's canonical serialization, not token estimates. Every case must assert both data and side effects. Do not use model-generated answers as semantic ground truth.

## Historical review performed for the original documentation change

**2026-10-15 annotation:** The walkthrough and host probes below describe the earlier documentation-only change, not the later generic runtime verification. Phase-A evidence is in the [verification map](verification.md); production semantic obligations are in [semantic acceptance](semantic-acceptance.md). No semantic-quality or live-pilot pass is implied.

A same-agent cold-reader walkthrough checked these paths using the contract and matrix (not an executable toolkit):

1. **Submission:** EX-01/05/10/11 locate authorization, readiness, JSON bounds, identity, and result type before any dispatch. Early setup is explicitly distinct from permission to execute.
2. **Partial continuation:** EX-12/13/14/19 identify the exact resume token, immutable identity check, pending-only default, failed-item opt-in, and lifetime retry cap. A completed batch can still contain failures.
3. **Disable during dispatch:** EX-20/21/29 distinguish a started attempt from an unattempted item and a reservation proven not dispatched. Cancellation does not silently restore allowance.
4. **Restart:** EX-24/28/30 identify the durable reservation, full liability on unresolved outcomes, disabled new epoch, expired handles, and fail-closed corrupt storage. No raw input/result persistence is needed.
5. **Branch navigation:** EX-25/26/37 separate all-entry cumulative accounting from generation-local workspaces, and distinguish same-session navigation from a fork's new identity.

The walkthrough found no remaining implementation-blocking policy decisions in these paths. This is a document consistency assessment, not independent review or runtime verification. The persistence-readiness restriction was explicitly approved by the user. Experimental limits, cooperative cancellation overrun, native logical-request accounting, single-writer session assumptions, and external library usage-reporting responsibilities are disclosed rather than hidden as performance or security guarantees.

Observed host evidence is limited to installed documentation/source inspection and the three local probes recorded in the contract (initial persistence, all-branch visibility, synchronous event callback). The future implementation must still run every acceptance case, especially duplicate physical library copies and failure injection. No live classifier, quality evaluation, cost benchmark, or native smoke test was run.

## Handoff and evaluation boundary

The next executable change must map each EX case to a test or a clearly documented host-integration test procedure. Semantic-family/search cases can use a minimal consumer adapter to test the shared core contract without implementing discovery. An opted-in native smoke test is separate from deterministic CI and is not marked passed when credentials are absent.

Compare the managed path with a plain native codemode batch on the same operational fixture before claiming value: interrupted completion, remaining provider invocations, reuse, shared allowance compliance, and frontier-visible result volume. Semantic precision/recall, model-specific cutoff calibration, realistic held-out labels, and release latency/cost gates belong to later evaluation work. These documents do not claim those gates have been met.
